**审阅对象**：[automation-api-analysis-plan.md](automation-api-analysis-plan.md)（方案复审稿 v2）
**审阅日期**：2026-09-29
**代码基线**：Windows `a9590b7`（v1.2.30 之后），Uno `57e555e`

## 0. 结论先行

1. **方向对，设计质量高，但对这个项目来说偏重。** 方案把一个本机、默认关闭、通常只有一个客户端的接口，按"公开平台 API"的标准设计（13 条冻结决策、4 个完成阶段、幂等缓存、事件水位与背压、两仓库双实现）。按原计划落地是数周的工作量，且大部分成本花在"还没有真实调用方"的能力上。
2. **"有没有必要"的答案取决于第一个调用方是谁，方案没有回答这一点。** 我认为最有说服力的理由不是"插件生态"，而是：**自动化行为测试**和**让 AI 代理直接编辑、并让人在旁边看着**。这两个用途决定了应该先做什么（见第 1 节）。
3. **有一个方案低估了的前置缺陷：编辑器不能忠实往返正文。** 你今天报的"切换一次阅读模式后源码变了"就是它的表现。只要这个问题在，接口读到的"最新正文"可能不是任何人写过的文字，接口写进去的正文也可能被改写。它必须排在所有接口工作之前（见第 3.1 节）。
4. **建议把 v1 缩成一个几天能做完、能立刻用起来的 MVP**，其余能力等真实调用方提出需求再加（见第 4 节）。

## 1. 问题一：现在做接口有没有必要

方案第 1 节的场景表是对的：只为"从外部打开文件"不值得做；要接触未保存正文、选区、实时设置，就必须有正式边界。但它没有说明**谁会先用**，于是只能把所有可能的调用方（脚本、桌面自动化、AI、测试、插件）都当成需求来设计。

从这个项目最近的实际工作看，有两个非常具体、现在就存在的需求：

| 需求 | 现状 | 接口能带来什么 |
| --- | --- | --- |
| **Windows 行为验证** | 可靠性审阅要求 R01–R04（刷新、切换、保存、备份）要有"能失败的行为测试"。这些逻辑绑在 UWP/XAML 里，单元测试需要大规模解耦，只能靠人工实测 | 一个能 `open → 输入/替换 → 切换标签 → 保存 → 读回磁盘字节` 的外部客户端，就是端到端测试驱动器。R01/F07 的"保存 A 等待时切到 B"这类竞态可以直接写成测试 |
| **AI 代理编辑 + 人观察** | 目前只能用 xdotool 模拟按键、截屏（做 README 动图时就撞上了"WebView 内容不进 x11grab"），或者让代理改磁盘文件、触发外部重载对话框 | 代理通过接口读最新正文、按版本写入，人看着编辑器实时变化 |

**建议**：在方案开头明确"第一个调用方 = 端到端测试客户端 + AI 代理（经 CLI 或 MCP）"。这会直接改变优先级：

- 测试客户端需要的是 `document.open/get/replace/save`、切换标签和读取状态，**不需要**事件订阅、背压和四阶段呈现回执。
- AI 代理最常用的编辑原语是"按文本定位替换"，而不是 UTF-16 偏移（见 2.2）。
- MCP 适配器应该比方案安排的第 5 阶段早得多，因为它是 AI 代理的实际入口。

如果这两个用途你都不打算近期使用，那么现在确实没有必要做这套接口；先把第 3.1、3.3 节里本来就是缺陷的问题修掉更划算。

## 2. 问题二（上）：作为"给程序用的接口"是否合理

整体合理：稳定英文标识、整数错误码加 `data.kind`、版本协商、显式目标 ID、`baseRevision` 冲突检查、不在错误里泄露正文——这些都是机器接口该有的。下面是需要修正或补充的地方。

### 2.1 选择 `Content-Length` 帧的理由不成立

方案 5.1 的第一条理由是"正文可能包含任意换行"。但正文是 JSON 字符串，换行会被转义成 `\n`，一条 JSON 消息本身永远不含裸换行。所以按行分隔的 NDJSON 完全能承载任意正文，也能在读取时限制单行长度（第二条理由同样满足）。

NDJSON 的好处是：PowerShell、Python、`socat`/`nc`、Node 几行代码就能对接，调试时可以直接手敲。`Content-Length` 帧对脚本调用方是门槛，只对"已经有 LSP 库"的调用方有利。

**建议**：v1 用 NDJSON（一行一个 JSON-RPC 消息，限制行长）。如果仍然选择 `Content-Length`，请把理由改成"与 LSP 工具链兼容"，而不是换行问题。

### 2.2 编辑偏移写死 UTF-16，对多数调用方不友好

UTF-16 对 .NET/JS 方便，但 Python 字符串按码点、Go/Rust 按字节，AI 代理则基本不数偏移。方案虽然要求 fixture 覆盖 emoji 和代理对，但这只是把出错的责任推给每个客户端。

**建议**：

1. v1 的主编辑原语改成**按文本定位**：`document.replaceText { documentId, baseRevision, find, replace, expectedCount }`，`find` 不唯一或次数不符时返回冲突。这和 AI 编辑工具的做法一致，对偏移单位不敏感，也天然防止改错位置。
2. `document.replace`（整篇替换 + `baseRevision`）保留。
3. 偏移式 `document.applyEdits` 延后；真要做时参考 LSP 3.17 的 `positionEncoding`，在 `system.initialize` 里协商 `utf-8`/`utf-16`/`utf-32`，而不是只支持一种。

### 2.3 `operationId` 幂等缓存在本机场景是过度设计

本机 IPC 几乎没有"请求到达、响应丢失"的情况。而且 `baseRevision` 已经让重试是安全的：第一次写成功后 revision 前进，重试会得到 `revision_conflict`，客户端重新读取就能看到自己的修改已经生效。`save` 本身是幂等的。

**建议**：`operationId` 保留为**可选的关联 ID**（用于事件的 `origin` 判断和日志），去掉"服务端缓存结果、同 ID 返回原结果"的要求。等真有网络网关再加。

### 2.4 四个完成阶段对调用方负担太重

`accepted/applied/presented/persisted` 加上 `waitFor` 参数和每个目标的呈现状态，调用方要理解 4×N 种结果组合。测试客户端和 AI 代理实际只关心两件事：**编辑器里是不是已经是这个 revision**，以及**磁盘上是不是已经写好**。

**建议**：v1 写操作默认返回"编辑器已应用"（带 `revision`、`contentHash`），`save: true` 时额外保证已持久化；`presented`（等一帧绘制）做成可选参数。宿主 XAML 侧的"已绘制"很难可靠检测，v1 不要承诺；页面侧用 `requestAnimationFrame` 两次即可近似。

### 2.5 两端设置名需要一张规范映射表

Windows 的设置是 `SettingsViewModel` 的属性名写进 `Settings.json`，Uno 是 `AppSettings`，两边命名和枚举并不一致（例如主题、启动行为）。方案要求"相同的设置 key"，但没有要求建立映射。

**建议**：阶段 0 产出一张"外部 key ↔ Windows 属性 ↔ Uno 属性 ↔ 取值"的表，作为 `settings.describe` 的数据源和两端测试的依据。

### 2.6 缺少的方法

- **`document.create`**：新建未命名文档（可带初始正文）。AI 代理写新文档、测试客户端构造场景都需要，方案只有 `open`。
- **状态读取里的大纲/标题列表**：代理定位"改第 3 节"时需要，`document.get` 可选返回。
- **CLI 的 `--json` 输出和稳定退出码**：方案强调 CLI 只是参考客户端，但脚本调用 CLI 时仍需要机器可读输出。

### 2.7 一处事实描述需要修正

方案 6.4 说"宿主驱动的 `SetMarkdown` 抑制 `MarkdownChange`"。实际代码（`Editor/index.tsx` 的 `setContentFromHost` 与 `onMarkdownChange`）是：先把 `markdownRef` 设为宿主给的文本，之后 Muya 上报的正文**如果和它相同**才不上报；**如果 Muya 把它规范化成了别的样子，就会作为 `MarkdownChange` 发回宿主**，文档被标脏。这恰好引出下一节的问题。

## 3. 问题二（下）：通过接口的修改能否实时显示给人看

方案 6.4 的缺口表我逐条核对过，基本成立。特别是 **Windows 多窗口设置多写入者**：`SettingsViewModel` 在 `Injection.cs` 里是 `AddScoped`（每窗口一个），每个实例在构造时各自 `new JsonSettingsStore(settingsFile)`，写同一个 `Settings.json`。这不只是接口的前提，**现在就是一个会让设置互相覆盖的缺陷**，应该独立修掉。

在此之外，还有几个对"人实时观察"影响更大的缺口。

### 3.1 编辑器不能忠实往返正文（最重要的前置缺陷）

> **已过时**：本节依据的故障已由 `7c02d10` 修复（见文首订正）。仍然成立的部分见第 8.2 节。

**证据**：

- 你今天报告：一篇含列表和 ` ```bash ` 代码块（代码块里有 `* test`、`# git branch` 这样的行）的文档，切换一次阅读模式后，源码变成了缩进错乱、代码围栏被破坏、内容重复的版本。
- `Editor/index.tsx` 的注释明确写着 "Muya normalizes its internal model"，并专门为 `FileLoaded` 保留了原始拼写；但之后的每次 `onMarkdownChange` 都会用 Muya 的序列化结果覆盖 `markdownRef`。
- 源码模式的正文取自 `markdownRef`；所以只要 Muya 在任何重新渲染（切模式、设置变化）时上报了与原文不同的序列化结果，宿主和源码视图就会接受它。

**对接口的影响**：

- `document.get(consistency: "latest")` 返回的可能是"Muya 认为的正文"，而不是用户或代理写下的文字。
- `document.replace(text)` 写进去后，读回来可能被改写；在出问题的输入上甚至是被破坏。方案用 `normalized: true` 标记来处理，但这只适用于无害的规范化（例如列表符号统一），对今天这种破坏性改写不够。
- `contentHash`/`baseContentHash` 会因为规范化而无故不一致，造成虚假冲突；文档会在没人编辑时被标为未保存。
- 对"人观察"而言，人看到的渲染结果和接口写入的文本不一致，接口就失去了可信度。

**建议**（作为阶段 0 的第一项，和接口无关也应该先修）：

1. 先定位阅读模式往返问题的根因，把上面那篇文档做成回归测试（编辑器已有 jest，可以做"载入 → 切模式 → 读回，字节不变"的用例）。
2. 确立原则：**宿主持有的文本是权威正文；只有用户在编辑器里的真实输入才能改变它**。宿主推送内容后、模式切换后，Muya 的重新序列化不能回写成正文变化。
3. 接口写入的内容，在未经用户编辑的情况下读回必须逐字节相同；做不到的输入（Muya 确实无法表示的结构）要在写入时报错，而不是静默改写。

### 3.2 整篇替换对"观察者"不友好

`SetMarkdown` 会让 Muya/CodeMirror 重建整篇文档。对正在看着的人来说，代理改了一个词，结果是：整页重绘闪一下、滚动位置和光标跳走、找不到刚才看的地方。大文档更糟——Uno 的注释里记录过 WebKitGTK 渲染 30 万字符要 43 秒，这时"等待 `presented`"会直接超时。

**建议**：

- 宿主收到整篇替换时先与当前正文做差分，只把变化的区间作为局部编辑交给编辑器（Muya 按块、CodeMirror 按范围）。这同时解决闪烁、滚动跳动和大文档性能。
- 保留观察者的滚动位置；变化区域短暂高亮一下，让人知道"刚才外部改了这里"。
- 这比"呈现回执"更决定观察体验，建议在阶段 2 与正文写入一起做，而不是只追求回执的精确性。

### 3.3 三种编辑模式下的行为未定义

同一个 `document.replace`，在所见即所得（Muya）、源码（CodeMirror）、阅读模式（Muya 只读）下走的是不同的编辑器和不同的规范化路径。方案没有定义：

- 阅读模式下是否允许接口写入（用户不能改，接口能不能改？改了要不要重绘？）。
- 模式切换发生在一次写入进行中时怎么办。

**建议**：v1 明确规定写入以文本为准，由宿主更新权威正文后再推给当前编辑器；阅读模式允许写入并重绘；写入期间暂缓模式切换。

### 3.4 人和代理同时编辑的可见约定

方案的页面侧二次冲突检查（`baseContentHash`）是对的，但它只能让代理的写入失败，不能让人知道"现在有程序在操作这个文档"。

**建议**：把方案 6.4 第 11 条的"可选状态栏提示"改为**必选**：有自动化客户端连接时，状态栏常驻一个"自动化已连接"标记（类似浏览器的"正受到自动测试软件控制"），外部写入时短暂显示来源。这既是观察需求，也是安全需求——用户能发现意料之外的连接。

### 3.5 设置变化的可见性

方案已覆盖主题、语言、快捷键需要语义化处理。补充两点：

- **设置对话框打开时**，控件是否会跟随外部修改刷新，需要逐项确认（很多控件只在打开时读取一次）。
- **阅读/源码模式切换**同时是设置和文档状态，并且会触发 3.1 的往返问题；在 3.1 修好之前，不要通过接口开放模式切换。

## 4. 分阶段建议（替代方案第 12 节的顺序）

| 阶段 | 内容 | 说明 |
| --- | --- | --- |
| **0. 先修本来就是缺陷的问题** | ① 阅读模式/模式切换的正文往返问题（3.1），加 jest 回归测试；② Windows 多窗口设置多写入者；③ Windows `DocumentTab` 加稳定 `documentId`；④ 两端文档 `revision`（只在真实正文变化时递增） | 不做接口也值得做。完成前不开放任何写入接口 |
| **1. MVP（先做一个平台）** | NDJSON JSON-RPC；`system.initialize/ping`、`window.list`、`document.list/get/open/create/focus`、`document.replace` 与 `document.replaceText`（带 `baseRevision`）、`document.save`；设置只开放少量窗口级项（主题、字号），不做多窗口广播；状态栏"自动化已连接"标记；CLI（`--json`、退出码） | 完成后立即用它写 R01–R04 的端到端测试，作为验收 |
| **2. 观察体验** | 差分式应用外部修改、保留滚动、变化高亮；页面侧应用回执（双 `requestAnimationFrame`）；撤销事务（一次调用一个撤销步骤） | 决定"人能不能看懂代理在做什么" |
| **3. AI 入口** | 在 MVP 之上做 MCP sidecar，把读、按文本替换、保存映射为工具 | 比原计划的第 5 阶段提前 |
| **4. 按需扩展** | 事件订阅（先轮询 `document.list` 的 revision 即可替代）、偏移编辑与 `positionEncoding` 协商、`operationId` 幂等、完整设置 store 与批量更新、另一平台对齐 | 有调用方提出需要时再做 |

**先做哪个平台**：

- 若第一目标是**测试 Windows 可靠性修复**，就先做 Windows——接口本身就是解决"Windows GUI 没法自动测"的办法。
- 若第一目标是**AI 代理编辑**，建议先做 Uno：它已有 `DocumentId`、共享设置实例，能在 Linux 上用 Xvfb + 窗口管理器无人值守地跑和测，迭代快得多；协议稳定后再移植到 Windows。

## 8. 对 v3 仍有的意见

### 8.1 设置接口仍会拖住 MVP

v3 的两个第一调用方（R01～R04 端到端测试、AI 辅助编辑）都不需要设置接口，但阶段 1 仍包含 `settings.describe/get/set`，而它依赖阶段 0 里最大、最不确定的改造：Windows 应用级设置 store、`ApplySettings/SettingsApplied`、已打开设置页同步。这正是 v3 风险表里的"MVP 再次膨胀"。

**建议**：阶段 0 拆成两条独立线：

- **0a 文档线**：往返门禁、`documentId`、revision、窗口/文档注册表。阶段 1 的文档 MVP 只依赖它。
- **0b 设置线**：多写入者修复（本身是缺陷，照常做）、映射表、apply handler。设置接口在 0b 完成后单独开放，不阻塞文档 MVP 和 R01～R04 测试。

### 8.2 精确往返只保证到用户第一次在可视模式编辑为止

`Muya/index.tsx` 的 `contentChange` 处理是：

```text
text = imported && markdown === imported.normalized ? imported.source : markdown
```

也就是说，只要 Muya 的输出还等于导入时的规范化结果，就换回原文；**用户在可视模式里第一次真正编辑之后，整篇正文就变成 Muya 的完整序列化结果**——列表符号、表格对齐、空行等规范化会在全文一次性生效，而不只是被编辑的那一处。

v3 的表述"没有用户编辑时逐字一致"在这个范围内是准确的。但第二个调用方的常态恰恰是"人也在编辑"：

- AI 写入 → 人在可视模式里改了一个字 → 全文格式被重排 → AI 下一次 `replaceText` 用的 `find` 可能因为格式变了（内容没变）而 `match_count_mismatch`，revision 之间出现大面积无关差异。
- 保存时写到磁盘的也是重排后的全文（这是 Typedown 现有行为，不是接口引入的，但接口会让它被看见）。

**建议**：

1. 在方案里写明这个边界，并在 MCP 工具说明中提示代理：`match_count_mismatch` 后先重新读取，`find` 尽量取短而唯一的内容片段，不依赖格式字符。
2. 增加测试：接口写入 → 模拟一次可视模式用户输入 → 读回，断言内容语义不变，并记录格式变化范围，让这个行为有基线。
3. 长期方向是按块局部序列化（只重写被编辑的块，其余块保留原文）。这是 Muya 层面的工程，不应进入接口计划，但它决定了"人和 AI 共同编辑"的体验上限。

### 8.3 R01/R03 的竞态测试需要确定性的注入手段

v3 要求端到端测试"保存 A 等待页面刷新时切到 B""最后一次输入尚在节流窗口时立即保存"。外部客户端无法让编辑器的刷新恰好停在某个时刻，只靠调用时序去撞，测试要么不稳定，要么从未真正触发竞态。

**建议**：增加仅在测试构建或调试开关下存在的 `test.*` 方法，例如延迟下一次 `FlushContent` 响应、暂停自动保存计时器；发布构建里这些方法不存在，`system.initialize` 也不报告。这样 R01/R03 才能写成"在缺陷回归时必然失败"的测试，满足 v3 自己定的完成标准。

### 8.4 `content_not_roundtrippable` 需要定义回滚

按第 6.2 节第 7 步，页面先应用内容、再回传正文由宿主比对。如果比对失败，页面已经显示了新内容，Muya 的撤销栈也可能已经变化。方案需要写明：比对失败时页面恢复到写入前的内容和撤销栈、revision 不变，并有对应测试。按 `importedRef` 的现有机制，纯宿主写入读回时应当总是原文，这个错误多半只在防御性路径上出现，但失败语义仍需确定。

## 9. 插件生态：按现在的设计还能做吗

### 9.1 结论

**能做"进程外的工具型插件"，做不了"真正的插件生态"。** 方案没有堵死后者（v3 把进程内插件和插件系统明确列为非目标、另行设计，这是对的），但有三件事应在 v1 契约里预留，否则以后要破坏性改动（见 9.4）。

### 9.2 插件生态通常需要什么，现设计覆盖了哪些

| 能力 | 现设计 | 说明 |
| --- | --- | --- |
| 读写文档、保存 | ✅ MVP | 外部程序（格式化、翻译、发布、AI）可以直接用 |
| 观察变化 | ⚠️ 轮询 | 事件订阅在阶段 3；插件生态会把它提前 |
| 作用于选区（"翻译选中文字"） | ❌ 延后 | `selection.*` 在阶段 3 |
| **在 Typedown 里注册命令、菜单、快捷键、状态栏、侧栏** | ❌ 没有 | 这是插件生态的核心体验。没有它，插件只能从命令行或外部窗口触发，用户在 Typedown 里看不到也点不到 |
| **钩子（保存前格式化、粘贴处理、导出后处理、打开时转换）** | ❌ 没有 | 事件只是通知，不能修改或否决 |
| 编辑器内扩展（新语法、新代码块渲染器、自定义渲染） | ❌ 非目标 | 见 9.3 的安全问题 |
| 生命周期（发现、安装、启停、随 Typedown 启动、崩溃隔离、更新） | ❌ 没有 | |
| 按插件授权（只读/可写、哪些文档、哪些设置） | ❌ 没有 | 现在是"同一系统用户全有或全无" |
| 跨平台 | ✅ | 同一协议 Windows/Uno 通用，这是进程外方案的优势 |

项目里其实已经有几个雏形扩展点：自定义主题（主题文件夹里的 CSS）、自定义 CSS 设置，以及 Windows 图床——它的 `AvailableImageUploadMethods` 目前只开放 PowerShell，本质上已经是"调用外部脚本"的插件。

### 9.3 编辑器内插件的安全问题

编辑器页面可以直接调用宿主函数：`ExportCallback`（会写文件）、`SetClipboard`、`OpenNewWindow`、`LoadImage` 等。方案 2.3 节也指出 WebView 协议"信任随应用发布的页面"。因此不能把第三方 JS 加载进现有编辑器页面——那等于把宿主桥交给了插件。

如果将来要支持编辑器内扩展，需要单独的隔离层（例如 sandbox iframe + 白名单 postMessage API）。在那之前，很多需求可以用进程外方式满足：例如"代码块渲染器"——插件接收某种 fence 语言的内容、返回 SVG/HTML，由编辑器沙箱化显示，就能覆盖 PlantUML、自定义图表之类的需求，而不需要第三方代码进页面。

### 9.4 现在就应在 v1 契约里预留的三件事（成本低，事后改代价高）

1. **连接必须是双向的。** 插件的命令回调（"用户点了你的菜单"）和钩子（"即将保存，是否修改"）都是服务端向客户端发请求并等待响应。JSON-RPC 和 LSP 本来就支持这种方向，但 `JsonRpcConnection` 和 `AutomationService` 的实现如果假设"只有客户端发请求"，以后就得重写连接层。v1 不用这个能力，但实现不要排除它。
2. **在 `system.initialize` 里预留授权范围字段。** 例如客户端声明 `requestedScopes`，服务端返回 `grantedScopes`。v1 一律全部授予，但字段形状先定下来，以后按插件授权时不改协议。
3. **稳定的客户端身份。** 现在 `client.name` 是自报的，只用于状态栏显示。插件需要安装时登记的稳定 `clientId`，用来绑定授权和它贡献的菜单项。v1 至少把字段定义好。

另外两条设计原则，届时再落地但现在应写进方案的"后续方向"：

- **界面贡献要声明式**：插件通过类似 `contributions.register { commands: [{ id, title, shortcut, menu }] }` 注册，由 Typedown 渲染菜单、在点击时回调插件；连接断开时贡献自动移除。插件不自己画界面。两端现在的菜单都在代码里写死（Uno 的 `BuildMenus`、Windows 的 XAML 菜单项），需要留出一块动态菜单区域。
- **钩子和事件分开**：事件是通知，可合并、可丢弃、有背压；钩子是同步请求，必须有超时和失败时的默认行为（插件挂了不能让保存卡住，这和 R03"刷新超时不能当作成功"是同一个教训）。不要把"保存前格式化"做成事件订阅。

### 9.5 建议

- 不要把 v1 扩成插件系统（同意 v3 的非目标）。
- 9.4 的三件事放进阶段 0 的协议设计，几乎不增加工作量。
- 自动化 MVP 跑通后，单独写一份插件设计文档。适合作为第一个插件的用例：
  1. **图床上传钩子**：Uno 至今没有图床，Windows 也只有 PowerShell 一种。把"上传图片"做成一个钩子，由外部插件实现 FTP/Git/OSS 等后端，两端不用各写一遍。
  2. **保存前格式化**。
  3. **外部代码块渲染器**。
  4. **"改写选中文字"类 AI 命令**：需要选区接口和界面贡献。

# 第三轮：对方案 v4 的意见

v4 已处理第二轮全部意见，其中几处比我原来的建议更好：自报 `client.id` 不作授权依据、图床做成有类型的 provider 而非通用钩子、barrier 使用"创建 → 等待命中 → 交错 → 释放"握手、回滚进入状态机。以下是剩下的意见，按重要性排列。

## 10. 剩余意见

### 10.1 "无编辑精确往返"主要由结构保证，真正的保真风险要在写入时就暴露

`Muya/index.tsx` 在宿主写入后执行：

```text
editor.setMarkdown(text)
importedRef = { source: text, normalized: editor.getMarkdown() }
```

之后每次上报时，只要 Muya 的输出仍等于 `normalized`，就换回 `source`。所以宿主写入的文本在没有编辑时读回必然逐字相同——这是由这段结构保证的，而不是 Muya 能忠实表示该文本的证据。由此有两个推论：

1. **阶段 0a 的"无用户编辑时三种模式精确往返"测试，实际验证的是"Muya 在重新渲染（模式切换、异步渲染 Mermaid/公式/图片）之间输出是否稳定"，不是保真度。** 这仍然值得测，但通过它说明不了 Muya 会不会在人第一次编辑时改坏文档。
2. **第 6.2 节第 7 步的逐字比对和 `content_not_roundtrippable` 在实践中几乎触发不了**：页面回报的就是 `source`。保真问题（例如 `7c02d10` 之前那种解析错误）会一直隐藏，直到人第一次在可视模式编辑，并被记到那次用户编辑的 revision 上。

**建议**：`importedRef.normalized` 在写入时就已经得到，它正是"人下一次编辑后文档会变成什么样"。比对 `source` 与 `normalized` 就能在写入时预知第 6.5 节的边界：

- 两者相同：无规范化，返回 `pendingNormalization: "none"`。
- 只有格式差异（列表标记、表格空格、空行）：接受写入，返回 `pendingNormalization: "formatting"`，让代理知道人编辑后会出现格式重排。
- 内容或结构不同（文字丢失、重复、块类型改变）：按 `content_not_roundtrippable` 拒绝并回滚。

这样该错误码有了真实的触发条件，第 6.5 节的边界也从事后意外变成调用方事先可见的属性。"格式差异"与"内容差异"的判定可以用同一个 Markdown 解析器分别渲染两者，再比较结构和纯文本。阶段 0a 的门禁重点应放在这个判定和"首次编辑后语义保持"的测试上。

### 10.2 回滚合并成一条路径

第 6.2 节第 8、9 步有两条失败路径：页面自行恢复并确认；恢复失败则进入 `editor_inconsistent` 再重载。宿主始终持有权威正文，而现有 `LoadFile` 本来就携带光标和滚动位置，所以"回滚"可以只有一种做法：**丢弃候选状态，用写入前的权威正文、光标和滚动经 `LoadFile` 重新载入页面**。

应用失败的实际原因多是 WebView 崩溃、页面重载或超时，这时页面本来就无法自行恢复；而正常情况下重载与页面自行恢复的结果相同。合并后少一个状态，也少一种需要测试的交错组合。`editor_inconsistent` 仍保留给"重载本身也失败"的情况。

### 10.3 测试构建不能进入安装包流程

方案要求用编译条件把 `test.*` 从 Release 移除。但这个项目的实际流程是：`hpbuild.sh` 在 hp 上打出本地安装包，再由 `hpcopy.sh` 复制到群晖供日常使用。只要有人用测试配置打了一次安装包，带 barrier（能暂停保存和刷新）的版本就会进入日常使用。

**建议**：

- barrier 放在单独的测试宿主程序集或单独的构建配置里，`build-local.ps1` 和 CI 在检测到测试配置时拒绝生成安装包。
- 测试构建的版本标签带明显标记（如 `TEST`），`system.initialize` 返回构建类型。
- 在阶段 1 的完成标准里加一条：Release 安装包中不存在测试程序集或 `test.*` 符号（例如检查打包输出）。

### 10.4 端到端测试的运行环境没有写

WebView2 需要交互式桌面会话。hp 上经 SSH 进入的会话不能显示界面，此前只能通过计划任务在登录会话里启动 GUI。方案要求用 R01～R04 做验收，却没有说明：

- 测试在哪里运行：hp 的登录会话（计划任务触发）、交互模式的自托管 runner，还是 GitHub 托管的 Windows runner。
- 如何启动 Typedown、打开自动化开关、收集结果（结果文件、退出码、失败时的截图和 `debug.log`）。
- 测试如何与日常使用的 Typedown 实例隔离（单独的数据目录和设置文件，避免改动真实设置、会话、最近文件和崩溃备份）。

不写清楚的话，测试驱动器做出来了，R01～R04 也很难被常规运行。建议在阶段 1 增加一项：给出可一键执行的 Windows 端到端测试脚本，并写明它的会话要求和数据隔离方式。

### 10.5 文档结构（次要）

方案已有 924 行，"审阅处理结论"表每轮都在变长。建议把它移到附录，并把协议规格（方法、schema、错误码、scope）单独成文。实施者需要的是规格和分阶段计划，不需要每次都读完讨论记录。
