# Typedown 外部自动化接口：审阅处理记录

**文档状态**：随实施计划 v5 更新
**更新日期**：2026-09-29


本附录记录三轮审阅意见的处理。当前实施约束以 [automation-api-analysis-plan.md](automation-api-analysis-plan.md) 和 [automation-api-spec.md](automation-api-spec.md) 为准；本表用于保留取舍理由，不作为重复规格。

| 审阅意见 | 处理 | 结论与理由 |
| --- | --- | --- |
| 明确第一调用方 | 采纳 | 首批调用方确定为 Windows 可靠性端到端测试和 AI 辅助编辑；因此 Windows 先于 Uno，MCP 先于完整事件系统 |
| 当前编辑器不能忠实往返正文 | 部分采纳并纠正事实 | 历史问题已由 `7c02d10` 修复；`reading-source-check.js` 在当前 bundle 上通过。该测试证明无真实编辑时的源文本映射稳定，不足以证明首次可视编辑保真；阶段 0a 因此同时保留稳定性门禁并新增规范化分类和首次编辑语义基线 |
| v1 改用 NDJSON | 不采纳 | JSON 字符串内的换行会转义，但合法 JSON 文档本身可以格式化为多行；NDJSON 必须额外强制单行编码。这里的调用方是程序和官方 CLI，长度帧能精确限流、检测截断，并可复用 LSP 风格工具；脚本易用性由 CLI 的 `--json` 提供。原稿中“正文含换行”作为主要理由不准确，已改正 |
| 增加按文本定位替换，推迟偏移编辑 | 采纳 | MVP 增加 `document.replaceText`；`document.applyEdits` 延后，并在需要时协商 `positionEncoding` |
| 去掉 v1 幂等结果缓存 | 采纳 | `baseRevision`、精确 hash 和写后重读足以保护 MVP 的正文写入。外部 `clientOperationId` 只用于关联；服务端仍生成内部 `operationId` 关联 WebView 回执。文档明确连接在响应前断开时结果可能不确定，客户端必须重读，不能盲重试非幂等创建操作 |
| 简化四阶段完成模型 | 部分采纳 | `applied` 和 `persisted` 仍是必要的一致性边界；`presented` 保留为 `reveal` 场景的可选近似回执。MVP 不公开通用 `accepted/applied/presented/persisted + waitFor` 状态机，也不声称能证明人看到了像素 |
| 增加设置映射、`document.create`、标题列表、CLI 机器输出 | 采纳 | 加入规范映射表、方法和 CLI 退出码要求 |
| 整篇替换必须自动差分为局部编辑 | 部分采纳 | `replaceText` 是 MVP 的局部编辑主路径；显式 `document.replace` 仍保留整篇替换语义。后续优化其页面应用方式、滚动和选区保持，但服务端不能在没有等价性证明时把整篇事务暗中拆成多个 Muya 操作 |
| 自动化连接提示改为必选 | 采纳 | 连接期间常驻提示，外部写入短暂显示来源，不弹阻塞对话框 |
| 设置先开放少量项但不做多窗口广播 | 不采纳 | Windows 当前每窗口各持一个 `JsonSettingsStore`，这正是会相互覆盖的可靠性问题。任何设置写接口都必须先完成共享 store 和广播；MVP 只缩小白名单，不能跳过一致性修复 |
| 事件订阅延后、MCP 提前 | 采纳 | 首版用查询和 revision 轮询；MCP 在 Windows 核心读写稳定后接入，完整事件流按真实需求增加 |
| 以 3～5 天、3～4 天估算各阶段 | 不作为排期采纳 | 审阅没有以代码拆分或 spike 支撑数字，Muya 局部编辑和多窗口设置迁移的不确定性尤其大；计划改用可验证的阶段完成标准，不把粗估当承诺 |
| 设置接口仍拖住文档 MVP | 采纳 | 阶段 0 拆成文档线与设置线；文档 MVP 不依赖共享设置 store，设置缺陷和设置接口独立交付 |
| 可视模式第一次真实编辑会切换到全文序列化结果 | 采纳 | 原样保留只保证到 Muya 输出首次偏离导入时的规范化结果；之后 revision 和 hash 以完整序列化结果为准，并可能出现无关格式重排。方案补充协作边界、调用方重读规则和行为基线 |
| R01/R03 需要确定性竞态注入 | 采纳 | 独立测试宿主增加一次性 barrier，而不是依靠 sleep 撞时序；正式项目与安装包不编译、不声明、也不接受任何 `test.*` 方法 |
| `content_not_roundtrippable` 缺少回滚 | 采纳并在第三轮简化 | 宿主在页面确认前不提交 revision、脏状态或撤销事务；失败统一由宿主用权威旧状态经 `LoadFile` 恢复，恢复加载也失败才进入隔离状态 |
| 为插件预留双向请求、scope 和稳定客户端 ID | 部分采纳 | 连接层预留双向 JSON-RPC，握手加入 scope 和持久客户端 ID；但自报 ID 不能绑定授权，scope 字段也不等于已建立插件权限。真正授权仍需安装登记和凭据 |
| “无编辑精确往返”不足以证明首次可视编辑保真 | 采纳 | 将该测试准确表述为源文本映射稳定性门禁；活动编辑器在写入时公开待规范化状态，阶段 0a 增加首次真实编辑后的语义保持基线。后台标签没有 Muya 实例，只能判为 `unknown/notEvaluated`；默认策略拒绝，显式接受后才提交，并在首次可视加载完成分类，不能伪造一个 `normalized` 结果 |
| 用同一个 Markdown 解析器渲染两份文本即可区分格式与语义差异 | 不采纳为安全判据 | 同一个缺陷可能同时影响两侧；纯文本/渲染树也会漏掉链接目标、代码块语言、HTML 属性、任务状态等语义。v1 只把逐字相同判为 `none`，已验证白名单判为 `knownFormatting`，其余判为 `unknown`；默认策略拒绝 `unknown`，调用方显式接受才提交；只有独立保守校验确认损坏才判为 `unsafe` |
| 回滚统一走宿主权威正文的 `LoadFile` 恢复路径 | 采纳 | 页面应用失败后由宿主使用写入前正文、光标和滚动重新载入；只有宿主恢复也失败才进入 `editor_inconsistent`，不再维护页面自恢复分支 |
| 测试 barrier 必须与安装包流程硬隔离 | 采纳 | 使用独立测试宿主/程序集；本地打包和 CI 拒绝测试宿主配置，正式包检查测试程序集、`test.*` 符号和 `AUTOMATION TEST HOST` 标识均不存在 |
| 明确 Windows WebView2 端到端测试环境和数据隔离 | 采纳 | 以 HP 已登录桌面会话中的计划任务为基线入口，提供一键脚本、独立数据目录/端点/互斥体，并收集结构化结果、退出码、截图和日志 |
| 拆分审阅历史与协议规格 | 采纳 | 本表移至独立审阅附录；方法、schema、错误码和 scope 移至独立协议规格，主文只保留分析、实施阶段和验收计划 |
