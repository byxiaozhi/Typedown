# 从 awarson2233/Typedown 借鉴的改进

对方的 fork（分支 `winui3-migration`）把宿主换成 WinUI 3、把编辑器内核从 Muya 换成 CodeMirror 6。
换底座的部分我们不跟，但它在工程方法上的几件事与内核无关，可以直接用在现有的 Windows 版上。
这份文件记录计划与进度；每条做完后在这里打勾并写明落点。

## 1. 文件字节保真 ✅ 2026-09-24（`1de5611`）

打开时按 BOM 认编码、记下换行符，保存时原样还原；编辑器内部只见 `\n`。
落点：`Dev/Typedown.Core/Utilities/TextFileFormat.cs`，接在 `FileViewModel` 的读写两端与每个标签页上。

## 2. CommonMark 规范回归 ✅ 2026-09-24

用 CommonMark 0.31.2 的全部示例（652 条）驱动编辑器，锁住解析与导出行为：每个示例导入 Muya 后导出
Markdown，再导入一次、再导出，两次导出必须相同（往返稳定），且渲染期间不得有脚本异常。与输入不一致的
示例记进基线文件，只有基线变化才算回归。

为什么值得做：这半个月我们动了 Muya 的图标渲染、表格对齐、删除处理、HTML 过滤器，每次都只能手工回归。

落点：`Tools/EditorBench/spec-check.js` + `Tools/EditorBench/spec-data.json`（规范示例）+
`Tools/EditorBench/spec-known.json`（基线）。

首轮结果：652 个示例全部无异常，15 个二次导入不稳定。随后逐条排查，改掉了四个真问题（见下），
现在只剩 3 个，都是一次性重排版、不丢内容的边角写法：制表符缩进的列表项、横线紧跟 setext 标题、
前后包着空行的缩进代码块。

### 顺带修掉的四个问题

1. **紧凑列表项里的引用块/代码块**会被多写一行"只有缩进的空行"，那一行按规范算空行，再打开时整个列表
   变成松散列表——打开再保存就改变了文件。
2. **列表项里用空行分开的两段被合成一段**。解析器把列表项内的行拼成一个段落时不看空行，所以
   "- 第一点\n\n  补充说明" 存回去变成 "- 第一点\n  补充说明"，渲染成一段。这是内容被改掉，不只是排版。
3. **setext 标题会把上面那一段吞进去**。`段落一\n\n标题\n---` 打开后变成一个标题，文本是"段落一\n标题"。
   原因是词法器判断"上一个 token 是段落就合并"，而它那份补丁把空行的标记 token 注释掉了，于是隔着空行也合并。
   现在空行会在前一个 token 上留下记号。
4. **代码块内容里含有三个反引号**时，导出仍用三个反引号收尾，代码块在中途就断了，后面的内容变成正文。
   现在围栏按内容自动加长。

还有一个只影响观感的：列表项之间的分隔空行以前写成"若干空格 + 换行"，现在写成真正的空行，省掉文件里
一堆行尾空格（引用块内仍然要带 `>` 标记，否则引用会断）。

排查方式记录在案：把 12 个不稳定示例各跑 8 轮开/存，11 个存第二次就定下来，只有一个每轮长 20 个字符、
永不收敛——真正危险的只有那一个，其余是一次性重排版。

## 3. 排版对比（style parity）✅ 2026-09-24

对方用两个无头浏览器同时装载新旧页面，逐块比较位置、尺寸、字体与行内样式，判据是漂移 ≤2px、尺寸差 ≤1px。

我们没有"新旧两套引擎"，但同一机制有两个用处，都做了：改动前后的自我对比（主题、图标、样式改动的回归），
以及 Windows 与 Uno 两个编辑器产物的直接对比。

落点：`Tools/EditorBench/style-check.js` + `style-fixture.md` + `style-known.json` / `style-known-dark.json`。
一份涵盖标题、列表、表格、代码、引用、公式、脚注、原始 HTML 的文档，量出 238 个元素的位置、尺寸、字体、
字重、前景与背景色；位置容差 2px、尺寸容差 1px，字体与颜色必须完全一致。

首次比对结果：两端的 js 与 css 产物哈希不同，但这份文档在 Windows 版与 Uno 版里**逐元素完全一致**。

## 3.5 编辑器内核的速度（测过了，不换）

他们把 Muya 换成 CodeMirror 6，收益是实打实的：只渲染视口，曲线是平的。我们随文档长度线性变差，十万字符
是分水岭。测量数据、每次按键的耗时拆解，以及"做节流与延迟渲染、不换内核"的决定，都记在
[editor-performance.md](editor-performance.md)。

## 4. 正文增量同步与版本号镜像

对方把"正文的真相在页面、宿主持一份带版本号的镜像"做成了完整状态机：每帧最多一条增量、版本跳号检测、
失步时整体重同步、保存前 flush。我们的 `postMessageDiff` 只做字符串差分，没有版本号，也没有失步恢复。

风险与收益都大，放在有实际丢改动的证据之后再做，或等两端宿主统一时一并处理。

## 5. 协议契约样例

`Tests/Protocol/samples/*.json` 每个消息一份完整报文，C# 与页面两侧的测试读同一批样例，任一端改字段就
会失败。我们的 `invoke / diffmsg / message` 是隐式约定，Uno 端桥接时吃过亏。

依赖第 4 项对协议的梳理，一并做更划算。

Core 时才体现，暂不做。
